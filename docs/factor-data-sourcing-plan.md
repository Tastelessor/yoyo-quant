## 1. 筛选标准

对用户提供的 109 项接口清单，按以下五条标准评估，任一不满足即降档或排除：

1. **独特性**：相对现有量价因子池（momentum/trend/volatility/volume_price/vwap 等）的信息增量；数据是否半私有/少人系统使用。
2. **预期差适配**：是否直接或间接服务"surprise = 新信息 − 事前预期"机制（用户选定的方向）。
3. **结构与可复现性**：是否结构化（数字/分类）、可 PIT（point-in-time）对齐、能进监控体系滚动评估；不依赖 LLM 输出稳定性（LLM 仅作后期增强层）。
4. **覆盖与时效**：全市场、日频或事件驱动；低频数据（季频）需能通过事件日转日频面板。
5. **成本**：是否已在项目接入 / 是否已有积分权限。

### 2.5 明确的缺口（清单之外）

清单中**没有** tushare"大模型语料"类接口：新闻快讯、新闻通讯（长篇）、上市公司公告、券商研究报告、国家政策库、e 互动问答、新闻联播文字稿。这些是"语义预期差 LLM 版"（形态③）的原始语料，tushare 存在但需要确认积分门槛（参考：`ths_hot` 需 6000 积分，语料类门槛只会更高）。**结论：LLM 语义版依赖积分升级，不阻塞规划，但阻塞落地时间表。**

### 2.6 接口接入优先级与放弃（v2 核对结论）

在分层验证（§3.4）视角下对 §2 接口清单的价值重排（用户确认）：

- **第一波接入**：`moneyflow` 系列（第一优先：项目实证背书 + 全市场覆盖 + 风格契合）→ `limit_list`/`top_list`（打板情绪/短线资金，风格核心，小盘高换手层预期强）→ `report_rc`（预期差锚点，但分析师覆盖偏大中盘，预期为 universal/大盘层因子）→ `share_float`/`stk_holdertrade`/`block_trade`（事件型，解禁对小盘影响最大，天然条件因子）。
- **排后（第二波）**：`hm_list`/`hm_detail`（游资席位，与 top_list 数据重叠，先验证情绪族再补）、`cyq_chips`/`cyq_perf`（先拉样本验覆盖与质量）、板块体系（`ths_index`/`dc_index`/`tdx_index`，工程量大，中期做一套 ths 作为事件传导骨架）。
- **不做因子（工具/风控）**：`stk_factor`（关卡 3 相关性基准集）、`stock_st`（ST 过滤，归 risk 层）。
- **放弃或降级**：`fina_audit`（非标意见样本极稀 <5%，过不了关卡 1 门槛；是排除性风险信号，归 risk 层而非 alpha 因子）、`pledge`（高质押是爆仓风险信号，同样降级到 B 档做风控/风格开关）、`disclosure_date`（信号弱、窗口窄）、`stk_surv`（口径杂、信号弱）、`ths_hot`/`dc_hot`（噪声大，与 limit_list/top_list 冗余，大概率过不了关卡 3 相关性关）。

## 3. 因子生成与筛选思路（问题 2）

### 3.1 总体思路：数据域 → 因子族 → 筛选流水线

不追求"一次性挖出神因子"，而是把数据源映射为**因子族**，每个族产出若干候选因子，统一经过同一套筛选流水线。目标不是单因子 IC 高，而是**IC 高 + 与现有因子池低相关**两个条件同时满足。

### 3.2 因子族设计（每族 2-3 个候选）

1. **预期差族**（`report_rc` + `forecast`/`express`）：
   - 预告/快报数值 vs 发布前一致预期 → 标准化 surprise（PEAD 逻辑）
   - 一致预期时序修正 revision（30/60 日）
   - 评级分布变化（买入占比上升/下降）
   - 预期效果：若有效，是现有 `earnings_surprise` 的**升级替代**，且天然与量价因子低相关。
2. **资金流族**（`moneyflow` 系列）：
   - 主力净流入/流通市值、大单净流入、连续净流入天数、资金流加速度
   - 预期效果：项目历史已验证该方向有增量，直接补因子池短板。
3. **筹码族**（`stk_holdernumber` + `cyq_chips`）：
   - 股东户数环比变化、获利盘比例、成本集中度
   - 预期效果：慢变量，与日频量价因子相关性低，是多样性收益的主力。
4. **事件族**（增减持/回购/质押/解禁/调研/审计/披露日程）：
   - 事件存在性、事件强度（金额/市值比）、事件后动量窗口
   - 预期效果：事件日稀疏，转日频面板后天然低相关；单个事件因子 IC 小但组合价值高。
5. **情绪/游资族**（龙虎榜/热榜/游资席位/涨跌停系列）：
   - 游资净买入、热榜新进、连板高度、炸板率
   - 预期效果：与用户"小型游资"风格直接匹配，短线情绪周期内有效，衰减快——正是生命周期监控要盯的品种。
6. **市场上下文族**（B 档数据）：不进个股因子池，进 context 模块做 regime/风格开关。

### 3.3 构造原则（所有因子族统一遵守）

- **PIT 优先**：事件数据一律用公告日/披露日对齐，禁止用报告期回填（`earnings.py` 已是此模式，新因子族沿用）。
- **日频面板化**：低频事件（季频股东数、事件型）通过"事件日赋值 + 前向填充至下一事件"转为日频截面。
- **标准化**：横截面 Z-Score 或 rank 归一，与监控体系 `compute_ic` 的 spearman 语义一致。
- **不做 LLM 前置**：LLM 只出现在后期增强层（见 3.6），主因子全部结构化可复现。

### 3.4 分层验证体系（新增，第一波即启用）

**动机**：因子挖掘经过全市场验证会把"适合特殊市场/小型选股单"的因子直接过滤掉。分层验证让这类**条件因子**（只在特定股票子集有效的因子）不被误杀。原则：**验证分层（事中、内置在挖掘流水线），使用后置（选股单事后按适用域匹配因子）**。

- **分层维度（事前定死，禁止事后挑层）**：
  - size：每日按流通市值 `circ_mv` 截面**三分位**（tercile）→ 大盘 / 中盘 / 小盘
  - liquidity：每日按换手率 `turnover_rate` 截面**三分位** → 高换手 / 中 / 低
  - 两维正交构成 **3×3 = 9 层**；"小盘 × 高换手"即用户选股单所在层
  - regime 分层（复用 `context.detect_regime`）**后置**：时间维度分层最易过拟合，第一波不启用
- **口径**：截面**相对分位**（每日最小的 1/3 为小盘），不用绝对阈值（绝对市值阈值会随市场涨跌失效）；分层是**层标签元数据**（每股票每天一个 size/liquidity 标签），不是新的独立股票池
- **数据**：tushare `daily_basic`（已接入 `fetch_fundamentals`，扩展 `fields` 加 `circ_mv`/`turnover_rate` 两字段即可；日频、按 trade_date PIT 天然对齐）
- **统计纪律**：
  - 维度事前定死（两维 9 层），禁止事后按表现挑层（挑子集本身是自由度，事后挑出的"有效"大概率是噪声/selection bias）
  - 9 层**全部如实报告**（因子值 + 每层 IC/t 面板），不只报最好的一层
  - 分层显著需多重检验校正（9 层 Bonferroni 或如实标注未校正）
- **通过标准（关卡 2 联动）**：全市场显著 **或** ≥1 个事前定义的层显著；输出因子**适用域标签**（如 `universal` / `small-high-turnover`），随因子元数据进监控，供策略层事后按选股单匹配
- **落点**：`evaluation.py` 新增分层 IC 纯函数原语（如 `compute_ic_by_layer`，放 `factors/ops/`）；层标签作为元数据列随因子值进入评估/监控（state 长表或独立 parquet）

### 3.5 筛选流水线（五关，与监控体系衔接）

| 关卡 | 内容 | 淘汰标准 |
|------|------|----------|
| 1. 数据质量 | 覆盖度（全市场覆盖率）、PIT 对齐完整性、事件样本量 | 覆盖率过低（如 <60%）或事件样本过稀（<100 条）直接淘汰；检查原语落在 `factors/mining/quality.py` |
| 2. 单因子统计（**含分层验证**，见 §3.4） | 日频截面 IC、滚动 t 统计量（复用 `factors/ops/evaluation.py` 的 `compute_ic` / `compute_rolling_tstat`）+ **分层 IC 面板**（`compute_ic_by_layer`，size × liquidity 两维 9 层） | 全市场滚动 \|t\| < 2 **且** 9 层中无一层显著（多重检验校正后）才淘汰；通过者输出适用域标签（universal / 层组合） |
| 3. 相关性过滤（**复用 Phase A，不新增**） | 与基准集算滚动截面秩相关 ρ 矩阵 | ρ > 0.7 淘汰。**实现复用 `factors/ops/correlation.py` 的 `compute_corr_matrix`**（Phase A 同一原语、同一阈值，配置读 `configs/factor_clean.yaml` 的 `corr_threshold`）；基准集 = Phase A 代表因子（`data/audit/factor_clean_a/representatives.json`，即"现有池去冗余后的代表"）+ `stk_factor` 基准（用户已确认 15000 分权限可用） |
| 4. 去相关增量（**新实现**） | 对基准集做**回归正交化**取残差，评估残差的增量 IC / 增量 t | 正交化后增量不显著则淘汰。注意：这是"对基准因子集回归正交化"，**与 `factors/ops/neutralize.py` 的行业中性化是两回事**——后者按行业 demean，不计算残差增量；正交化纯函数新落 `factors/ops/orthogonalize.py`（与 evaluation/neutralize 并列的操作原语）。**落地前置（YAGNI）**：先跑通关卡 3 + Phase B OOS，确认相关性门槛与时序验证仍漏掉"低相关但共线的组合噪声"再实现；关卡 4 与关卡 3 / Phase B 信息重叠，过早实现有过剩风险 |
| 5. 生命周期监控 | 进入 active/decaying/dead 状态机，滚动跟踪 | 按监控体系规则切换（复用既有 `factor_monitor`，入池清单交回监控即可） |

> 注意：关卡 3 的复用是 v2 修订的核心——本规划写于 Phase A 完成之前，原文把关卡 3 标为"新增"，但 Phase A（`factor_clean.py` + `correlation.py`）已用同一阈值 0.7 实现全市场去冗余（13 候选 → 4 代表，产物 representatives.json）。新因子挖掘时直接与 representatives.json + stk_factor 算 ρ 即可，不另建相关性流水线。关卡 4 回答"低相关小 alpha 因子如何不被误杀"：先过相关性关，再做增量评估，而不是只比单因子 IC。

### 3.6 LLM 增强层（数据到位后，非前置）

预期差族落地并验证后，若确认"surprise 机制"在 A 股有 alpha，再上 LLM 形态③：
- 输入：公告原文（需语料接口积分）
- 角色：**数值提取器**（读公告提取盈利指引/区间），而非情感分类器
- 对比：提取值与事前一致预期（report_rc）做差 → 文本增强 surprise
- 理由：情感对比存在风格漂移/频率错配/输出不稳定三个结构性问题（详见会话讨论），数值提取规避了它们；LLM 只做提取不做判断，把不稳定性降到最低。

### 3.7 预期效果

- **因子池结构**：从"量价同质"变为六域组合——量价（已有）+ 资金流 + 预期差 + 筹码 + 事件 + 情绪/游资，每域 2-3 个互不相关因子。
- **多样性收益**：各域相关性低（信息源不同：价格/资金/预期/行为），组合层面分散真实存在，解决"实际可用仅 1 个因子"的问题。
- **供血循环**：配合因子生命周期监控（活跃 2-8 个月就换），因子族提供持续候选池，支撑"每月换因子"策略。

## 4. 与现有系统的衔接

- **数据层**：新增数据源按 `src/data/` 现有模式接入（fetcher + parquet 缓存 + PIT 清洗），仿 `earnings.py` 先例**每数据域一个模块**（`report_rc.py` / `moneyflow.py` / `holdernumber.py` 等）；`earnings.py` 的 surprise 管线扩展 report_rc 锚点，构成预期差族的数据基础。分层验证所需 `circ_mv`/`turnover_rate` 由既有 `fetch_fundamentals`（daily_basic）扩展 fields 提供，不新增数据源。
- **因子层**：新因子族注册进 `factors/registry.py`（`@register_factor`，仿 `builtin/earnings.py` passthrough 先例——因子实现吃 data/ 管线产出的 DataFrame，不 import `data/` 模块），被监控体系 `list_factors(kind="single")` 动态发现。
- **筛选流水线**：五关编排落在 `factors/mining/pipeline.py`（新增域，结构见 §6）——复用 `factors/ops/evaluation.py`（关卡 2，含新增分层 IC 原语 `compute_ic_by_layer`）与 `factors/ops/correlation.py`（关卡 3）、新增 `factors/ops/orthogonalize.py`（关卡 4）、新写 `factors/mining/quality.py`（关卡 1）；关卡 5 为出口，入池清单（含适用域标签）交回既有 `factor_monitor` 滚动跟踪（mining 不 import `analysis/`，维持单向依赖）。
- **存量链路接管（v2 补全）**：新因子过五关入池后，自动被既有清洗/评估流水线接管——`yq factor clean-a`（去冗余）→ `clean-b`（walk-forward OOS 验证）→ `clean-c`（合成信号对比），不另建平行流水线。
- **不涉及**：strategies / portfolio / risk 层（用户当前聚焦因子挖掘，消费层暂不动）。

## 6. factors/ 目录结构变更（因子挖掘落点）

因子挖掘功能（数据源因子化 + 五关筛选流水线）归入 `src/factors/` 域。目录结构如下——**既有部分零改动，全部为新增**：

```
src/factors/
├── registry.py          # 因子注册表/调度（不变）
├── operators.py         # 通用算子原语（不变）
├── builtin/             # 标准因子实现：量价 + 基本面（不变，13 个文件）
│   └── earnings.py      #   先例：passthrough 注册（data/ 算好，这里注册接口）
├── ops/                 # 对因子的操作原语（不变 + 1 新增）
│   ├── evaluation.py    #   IC / 滚动 t / 分层 IC（关卡 2 复用 + compute_ic_by_layer 扩展）
│   ├── correlation.py   #   相关矩阵 / 聚类 / 代表（关卡 3 复用）
│   ├── neutralize.py    #   行业中性化（与关卡 4 正交化区分，不改动）
│   ├── orthogonalize.py #   ★ 新增：对基准因子集回归正交化 + 增量 IC/t（关卡 4）
│   └── ...              #   cache / oos / synth 等既有
└── mining/              # ★ 新增：因子挖掘域
    ├── pipeline.py      #   五关筛选流水线编排（关卡 1→4，出口入池清单）
    ├── quality.py       #   关卡 1：数据质量检查（覆盖度 / PIT 完整性 / 事件样本量）
    └── sources/         #   各数据源因子化（@register_factor 注册，被 list_factors() 动态发现）
        ├── expectations.py  #   预期差族（report_rc 一致预期锚点）
        ├── moneyflow.py     #   资金流族
        ├── chips.py         #   筹码族
        ├── events.py        #   事件族
        └── sentiment.py     #   情绪 / 游资族
```

**设计理由：**

- **零破坏**：builtin/ 13 个标准因子、ops/ 既有原语、analysis/ 的 Phase A/B/C 编排全部不动；mining/ 是纯新增，不迁移任何既有代码。
- **职责划分**：builtin/ = 标准因子（量价/基本面，吃 ohlcv）；mining/sources/ = 另类数据源因子（低频/事件型、PIT 面板化，与量价因子本质不同）；ops/ = 可复用操作原语；mining/ = 挖掘流程编排。
- **依赖单向**：mining/ 只吃 data/ 产物（DataFrame 与 parquet）与 monitor 产物（state.parquet），不 import `data/`、不 import `analysis/`——维持现有三层解耦（factors/data/analysis 互不 import，靠 DataFrame 与文件交互）。关卡 5 出口化：入池清单交回既有 monitor，避免反向依赖。
- **data/ 扩展（配套）**：新增数据源 fetcher 放 `src/data/`（仿 earnings.py，每数据域一模块），不进入 factors/——数据获取/清洗职责不变，factors/ 只新增"因子化 + 筛选"。
- **边界说明**：`analysis/factor_clean|oos|synth`（Phase A/B/C 清洗评估编排）保持原位，属 analysis 业务编排层；factors/mining/ 承载"新数据源挖掘"域，两者通过产物文件（representatives.json / state.parquet / 信号 parquet）衔接，不构成职责重叠。
